# Internal-controls module (how Precog runs inside the PMS)

> Source: generated from the approved consolidation plan (planning session of 2026-09-03; workflow `wf_8edc6cab-3ac`, 44 agents). The evidence behind every claim is under `knowledge/reviews/`. Legal statements carry one of four labels: PRIMARY, SECONDARY, REPO, UNVERIFIED (see `docs/11`).

## Controls integration (how Precog runs inside the PMS)

**Event spine.** Every repository mutation inserts a `domain_event` row in the same transaction: role granted/revoked, user deactivated, credential expired, ledger posted (kind, amount, reason, poster, effective vs posted date, hour, location), ledger reversed, allocation made, refund posted, approval requested/decided/waived, exception created/expired, deposit prepared/closed, bank transaction imported, reconciliation closed/variance/cleared, claim submitted/denied/appealed/voided/written off, procedure deleted, appointment deleted/moved, vendor created/changed, payment released, encounter signed, chart event, export performed, disclosure recorded, PHI read (volume), new device login, chain verification result, control policy changed. `pg-boss` consumers fan these to the controls engine, detectors, digest, notifications, and webhooks. The engine never reads demo data and never reads the browser; a `PracticeState` builder assembles what Precog's functions expect from live rows.

**Segregation of duties from real grants.** The current view over `user_entitlements` is the `RoleAssignment[]` input to `detectSodConflicts`. It runs synchronously on every role event and nightly, upserting `sod_findings` keyed on (rule, person set), closing findings that no longer exist, reopening recurrences, with `mitigatedSodRuleIds` from the active control policy injected so enabling a dual-release channel visibly lowers and reclassifies the linked conflicts. **Enforced:** the role-grant API refuses a grant that would create a critical conflict unless the actor records a control decision (accept residual or compensate, with a review date) in the same request; a tenant may elect the stricter "grant sits pending until a distinct second admin decides" mode. Setup seeds the role templates and shows the conflicts before the first login is issued. COSO Principles 9 (assess change) and 11 (technology controls) flip from hard-coded weak to continuously monitored because grants, terminations, MFA coverage, and shared-device posture are observed events; a terminated user still holding grants is a finding.

**Dual release enforced in the transaction.** The ledger posting service is the only writer of `ledger_entries`. For adjustment, write-off, refund, reversal, transfer, and for the vendor, ACH, check, deposit, and payroll channels, `postGuarded(channel, request)` loads the tenant's active policy and exceptions and runs `evaluateRelease` inside the transaction:

| Verdict | Action |
|---|---|
| `below_threshold`, `approved_single`, `approved_exception` | post |
| `needs_second` | insert an `approval_requests` row with the frozen evaluation, post nothing, return 202 with one line + one control |
| `approved_dual` (a distinct, role-eligible second approver decided via compare-and-set; distinct person re-checked server-side and by CHECK constraint) | the worker executes the held posting with `approval_request_id` stamped |
| `blocked_same_person`, `blocked_role`, `blocked_missing_second`, `blocked_policy_off` | roll back, return 403 with `reasons[]` and `nextSteps[]` |

A BEFORE INSERT trigger re-checks that any approval-required entry carries an approved request, so no code path can bypass the service. Exceptions (raise / lower / force / waive) require the owner role, a residual note, and an effective window; waive auto-expires; the active-exception summary surfaces expiring and standing exceptions on the owner home and in the monthly digest so a temporary raise cannot quietly become permanent. Owner overrides exist but are ledger-annotated, appear in the digest and the CPA export, and lower the Control Activities score. Denial suppression: a write-off whose claim events show a denial with no appeal routes through dual release regardless of amount, and the person who submitted the claim cannot post it.

**Hard SoD blocks at action time (a small, named set).** Full separation is arithmetically impossible in a six-person office, so `withGuard` refuses only critical pairs at runtime: whoever posted payments or prepared the deposit for a business day cannot clear that day's reconciliation variance; self-approval of vendor master changes; self-approval of payroll; requester = approver. Every other conflict is detected, scored, and requires a dated decision but is not blocked. For one-owner, one-office-manager practices the variance rule degrades to owner-only clearance rather than being disabled, and the degraded state is itself a finding.

**Independent reconciliation, measured.** Bank transactions come from an aggregator feed (Plaid or Finicity class, under data-processing-agreement and BAA review) or from OFX/CSV statement import. `reconciliation_runs.independent` is computed (the closer held no custody or recording activity that day); detection lag is measured in days between posting and matched bank transaction; match rate within 48 hours is stored. These feed the residual engine's control effectiveness as **measured operating effectiveness** alongside configured **design effectiveness**; COSO distinguishes them and so does the UI. The reconciliation logic lives in the sealed verifier package so the system policing itself is at least tamper-evident.

**Detectors (recorded, batched).** Nightly and event-driven jobs write `control_findings`: refunds above threshold lacking an approval id (should be impossible, so it is a chain-integrity alarm); postings outside location business hours; reversals or adjustments dated more than N days before posting; adjustment-to-production ratio per reason code per role against the practice baseline; void and reversal velocity; duplicate patient payments; deposit-batch vs bank gaps; unmatched bank lines older than 48 hours; sole ownership of a critical process; copy-forward documentation clusters; and, in Phase 4, the forensic suite (Benford first and second digit, round-number bias, duplicates) framed as "worth a look" control-test results. Dental's digest rules govern reporting: batched weekly, minimum sample sizes, systemic-share re-scoping, person-scoped detail readable only by the owner and a designated reviewer seat. No output is ever phrased as an accusation.

**Scoring, COSO, journal.** The typed controls registry, measured effectiveness, and derived staff composition (team size from active users, sole-owner count from single-point-of-failure detection, tenure from hire date, segregation from `segregationHealth`) feed `portfolioSummary` and `assessCoso` nightly and on control events, frozen into `control_snapshots` stamped with `SCORING_VERSION` and `CONTROL_RULEBOOK_VERSION` so a weight change never regrades history. Every finding, score, and principle carries a deep link to the rows. `tornadoSensitivity` and the cascade simulator become the settings-page "what if I turn on dual approval for write-offs" preview with dollar deltas labelled directional until calibrated. `control_decisions` is the append-only, owner-attributed control register; overdue reviews appear on the owner home; COSO Principle 17 is literally "open findings without a decision." The journal, approvals log, exception table, and hash-chained event stream together are the evidence pack for a CPA, carrier, or OCR, rendered as plain sentences.

**Where enforced vs recorded (shown in-product).** Enforced (refuse): dual release on money-moving entries; critical-conflict grants without a decision; the named runtime SoD set; requester ≠ approver; BAA-gated connector enablement; PHI egress classifier on AI and export; note-signing gates (killers, licence scope, supervision corroboration); MFA, unique identities, server idle timeout; immutability of ledger, approvals, decisions, and events at the DB role. Recorded and surfaced: SoD findings, anomaly signals, COSO and residual scores, leading indicators, decision journal, compliance tasks, PHI access review. Everything advisory says so. A channel whose data the PMS does not yet hold (payroll, until the Phase 4 payroll-provider integration) is shown as **external / attested**, never as enforced, and is excluded from scores, so the table can never show a false green.

## Feature-layer amendments (2026-09-03)

Adopted from `docs/13-innovation-and-intuitiveness.md` (the feature workflow's synthesis and its critique). Where an amendment conflicts with text above, the amendment governs.

- Exception scopes gain 'hours' (per location, per weekday, server clock) and 'vendor_state'; default policy holds refund/adjustment/write-off outside hours at any amount, excluding processor-initiated refunds. Add the walk-over approval session (60-second, single-entitlement, PIN + TOTP, disabled on operatory profiles) and the phone card contents (request id only in push; denial-no-appeal line). Add vendor quarantine as a state the evaluator reads and 'first payment after any bank-detail change is always dual'. Independent reconciliation gains a three-state grade (independent | same_hands | stale_import) and EFT matching by TRN with many-to-one tolerance falling to amber. Add the reversal-and-repost correction pair (no 'correction' kind), the late-first-posting path (posted_after_close and closed_day_id, never corrects_entry_id), and two practice-level counts, 'changed after close' and 'postings into closed days', each excluding worker-actor ERA and import rows. Decision review: measured-effect sentence from domain_event, isDateActive expiry, unreviewed decision → finding, monthly batching. Detectors: cover grant closes on observed use; 'On leave' switch enforced by withGuard; reason-code drift card links fee-schedule and plan changes in window; tip routing excludes the owner server-side (two-party reveal deferred). Enforced-vs-recorded table gains: consent-scope refusal, self-pay restriction hard block, contradiction S0 at File and Submit, for-dentist tag disposition gate, plain-language delivery gate on print/portal, prior-period refusal, vendor quarantine ('enforced on recorded releases; bank rail external'), imaging-without-interpretation on referral send. Record explicitly that no reconciliation drill runs in production; the planted skim runs on a simulated month.
- From the critique: the hours scope and the changed-after-close count apply only to human-actor postings; a CI test asserts that an overnight 835 fixture produces zero approval requests and zero changed-after-close rows.
- From the critique: the CPA seat is split. The aggregate package, the question verb, and attestations need no BAA and carry payer ids and trace numbers only; patient-level drill-down and named bank reconciliation are refused at grant time until a countersigned BAA row for the firm exists, with the refusal rendered through the Refusal component.
- From the critique: the desk PIN on Post mints or resumes the second coordinator's own server session for the single posting (the 60-second single-entitlement session designed for walk-over approvals); a PIN never annotates another person's session.
- From the critique: the S0 chart/note/claim contradiction has no reason-coded override; the only exits are the three 'Use this' corrections through each source's normal path, or a rule change under `RULESET_VERSION`.

Since Increment 1.45 the practice governs its own reason codes at `/reason-codes` (anyone who posts may read them, the administrator changes them): `ledger_entries.reason_code` is a foreign key into `reason_codes (tenant_id, code)`, so the code never changes and a code in use is retired rather than removed — retiring clears `active`, takes it off the forms, and leaves every entry citing it readable, which is the only thing the key permits and the only honest treatment of history. The label is free to change because nothing keys on it, `prior_period` may be relabelled but never retired (the closed-month refusal admits a correction only under it), and each of adopt, relabel, retire, and restore is a chain event. The posting and correction forms are built from the rows rather than from a constant, and the screen shows how many entries cite each code, which is the reason a code is retired rather than deleted. The table needed no migration for that: it has carried `active` and FORCE RLS since migration 0010. Since Increment 1.46 a reason also carries its own dual-release threshold (migration 0035 makes `requires_approval_over_cents` nullable so its three states are distinguishable: null = the channel’s figure governs, 0 = every posting under that reason waits for a second person, N = a second person above N cents; every existing row backfills to null, which is the truth about rows nothing had ever read). The effective threshold is `least(channel, reason)`, so a reason only ever **tightens** — one that could loosen would let a practice undo dual release by inventing a reason. The database enforces it in `ledger_entries_requires_approval` (the whole current function carried forward, after-hours hold and correction branch included, with `GRANT SELECT ON reason_codes TO app_append` for the held-release path) and the posting and correction services tighten the policy they hand the engine by the same rule, so the practice meets a hold in words rather than a crash. A `raise_threshold` exception is untouched: it carries a decision and a review date, so it still licenses up to its own figure.
